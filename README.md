# 业务侧 AI Builder 招聘证据与追问助手｜交接说明

## 1. 项目目标与交付物

本项目是“业务侧 AI Builder”招聘场景的最小样板。它不替代任何招聘决策，而是帮助 HR、面试官和用人经理：

- 按 S1—S5 岗位成功标准整理候选人材料与面试记录；
- 区分候选人自述、面试观察、推断与证据缺口；
- 标记反向证据、不同面试官记录冲突、敏感信息、隐私请求和提示注入；
- 生成下一轮行为面试追问，并指定建议的主责角色；
- 保留人工审核、纠正、拒用和最终决策责任。

主要文件：

| 文件/目录 | 用途 |
| --- | --- |
| evidence-assistant/app.py | 分析规则、输入校验、风险检测和 JSON 输出 |
| evidence-assistant/server.py | 本地工作台服务 |
| evidence-assistant/index.html | 三步交互界面：导入材料、补充面试记录、审阅行动 |
| evaluation1/test-dataset.json | 17 条离线评测用例 |
| evaluation1/run_evaluation.py | 批量运行 17 条用例的脚本 |
| results.json | 批量评测的实际运行结果 |
| 01-diagnosis.md ~ 04-value-evaluation.md | 场景诊断、未来流程、人机边界与价值评估 |

## 2. 如何在新环境运行和验证

### 前置条件

- Windows、macOS 或 Linux；
- Python 3.10+；
- 不需要 API Key，不需要安装第三方包。

### 启动工作台

在项目根目录执行：

    py evidence-assistant/server.py

如系统没有 py 命令，可使用：

    python evidence-assistant/server.py

浏览器打开：

    http://127.0.0.1:8080

使用路径：

1. 在“导入材料”页上传 .txt、.md、.json 文件，或粘贴候选人材料；
2. 输入候选人编号，点击“下一步”；
3. 在“补充面试记录”页逐条补充技术面、业务面、HR 或用人经理记录；
4. 点击“生成证据卡与补问建议”；
5. 在结果页审阅 S1—S5 的支持/反向证据、来源、置信度、缺口和风险；
6. 由面试官点击“标记需补问”或“人工确认”；最终招聘决定仍由人作出。

### 运行离线评测

    py evaluation1/run_evaluation.py

该脚本读取 17 条测试用例并写入根目录 results.json。当前基线结果为 15/17 通过；EV1-007、EV1-008 为已记录的失败案例，详见 04-value-evaluation.md。

## 3. 模拟材料事实与本方案假设

### 来自模拟材料的事实

- 岗位需要同时具备业务场景诊断、AI 工程打样、人机协同与风险意识、业务共创推进、评测复盘与能力交接等能力；
- 当前招聘存在标准不统一、重复提问、证据不完整、面试官分歧和入职表现不回流的问题；
- AI 可以整理证据、发现遗漏、提示矛盾和建议追问，但不得独立作出录用、淘汰、定级或薪酬决定；
- 年龄、性别、婚育、民族、籍贯、照片、健康、学校、前公司和年限不能作为能力结论；
- C-017 的量化效果、真实使用量、个人职责边界、权限隐私和交接效果均属于待验证信息。

### 本项目的设计假设

- S1—S5 可作为该岗位面试分工和证据归类的初始标准，但其权重与预测效度仍需真实招聘验证；
- 技术面主要负责 S2/S3，业务面主要负责 S1/S4，HR/综合面主要负责 S5 和跨轮缺口；实际分工可由负责人调整；
- 关键词和规则可作为最小样板的证据初筛方式，但不能等同于语义理解或最终能力判断；
- 面试官会审核系统摘要、补问建议和风险提示，并对错误结果作出纠正；
- 入职表现可在获得授权和满足数据治理要求后，以脱敏方式回流，用于校准标准和题库。

## 4. 交给业务侧 Agent Driver 后需要配置和维护的内容

Agent Driver 是业务侧的日常维护责任人，不拥有招聘决定权。其主要工作包括：

1. **标准与题库配置**
   - 维护经用人经理/HR 批准的 S1—S5 定义、主责角色、追问模板和反向证据模式；
   - 新增或修改标准时记录版本、负责人、生效日期和回滚版本。

2. **权限与数据治理**
   - 确认允许进入系统的材料范围、候选人数据访问权限、留存期限和脱敏要求；
   - 发现无授权个人信息、敏感信息或异常材料时停止进入分析，并升级 HR。

3. **评测与回归**
   - 每次改动规则后运行 evaluation1/run_evaluation.py；
   - 将人工纠正、误判、漏判和新的注入模式整理为回归用例；
   - 未达到既定质量门槛时回滚至上一个批准版本。

4. **运行监控**
   - 定期查看 evidence-assistant/logs/assistant.log；
   - 关注输入错误、异常失败、风险命中、人工纠正率和问题采纳率；
   - 系统故障时使用人工面试记录模板兜底，不丢失原始证据。

## 5. 如何教业务人员发现错误、反馈和更新规则

业务人员无需修改代码，可按以下方式参与：

| 场景 | 业务人员动作 | Agent Driver 后续动作 |
| --- | --- | --- |
| 摘要不忠实于原话 | 点击“人工确认”前先修正，保留原始来源 | 记录为分类/摘要误差样本 |
| 系统把自述当作事实 | 标记“需补问”，要求补充角色边界、数据口径和佐证 | 增加自述降级规则与回归案例 |
| 面试官记录冲突 | 不强行选择一方；发起补问或升级用人经理 | 沉淀冲突模式与升级模板 |
| 追问无关或重复 | 拒用建议并说明原因 | 更新题库归属与去重规则 |
| 出现敏感信息/隐私请求/注入 | 停止使用该段作为能力判断依据，通知 HR | 完善拦截模式并复测 |
| 系统执行失败 | 使用人工模板继续记录，保留错误时间和输入类型 | 查看日志、修复并回归测试 |

规则更新流程：提出问题 → Agent Driver 记录案例和建议 → HR/用人经理批准 → 修改规则/题库 → 批量回归 17 条与新增案例 → 通过后发布新版本；任何一步不通过均回滚。

## 6. 如果再多一天，优先补什么

优先修复 EV1-007 与 EV1-008 暴露的证据逻辑问题，而不是先扩大功能范围。

原因是这两个问题直接影响招聘判断风险：

- EV1-007 会把“我主导/我推动”类候选人自述高估为业务共创能力事实；
- EV1-008 会把缺少基线、统计周期和测量方法的量化描述高估为评测与复盘能力。

优先工作顺序：

1. 候选人材料默认降级为 self_claim；只有面试观察、作品、数据或其他可核验来源才可支持 high；
2. 为量化结果增加“基线、口径、周期、来源”完整性检查；
3. 修复后重跑 17 条，再补至少 5 条多轮面试回归案例；
4. 达到离线门槛后，再扩展上传格式、跨轮去重、面试分工和结果回写等完整工作流功能。

## 7. 为什么当前结果不能直接用于真实招聘决策

当前结果**不能直接用于真实招聘决策**，只能作为面试准备和人工审核辅助，原因包括：

- 规则引擎仍存在两项已知误判，当前离线通过率为 88.2%，未达到项目设定的 ≥95% 试运行门槛；
- S1—S5 的权重和与入职表现的真实相关性尚未在业务中验证；
- 尚未建立真实候选人授权、数据留存、访问权限、人工复核时限等正式治理机制；
- 系统不具备、也不应具备录用、淘汰、定级或薪酬决定权；
- 真实场景必须保留用人经理最终决定、HR 合规审查、面试官原始记录核对和可回滚的人工流程。

因此，当前正确使用方式是：将它用于结构化证据、发现缺口、减少重复问题和生成后续追问；任何招聘决定必须由授权人员基于已确认的原始证据作出。
